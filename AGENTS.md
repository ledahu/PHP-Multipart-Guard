## What the project is

An Apache 2.4 rule set, no extra module, that:

1. blocks `multipart/form-data` requests on every URL except an allow-list,
   before PHP runs (PHP parses multipart before any script code);
2. on allowed URLs, accepts only the browser format (POST, one clean
   `multipart/form-data; boundary=...` header, Content-Length present,
   size ≤ limit);
3. refuses any POST whose body is bigger than PHP's `post_max_size`, so PHP
   never emits its early "POST Content-Length exceeds the limit" warning
   (early diagnostics are a CVE-2026-109619 consumer).

Modes: BLOCK (default) and OBSERVE (decisions logged only;
LimitRequestBody stays active). Decision is in env var `MPG`
(`allow`, `deny_not_allowed`, `deny_method`, `deny_bad_ctype`,
`deny_no_length`, `deny_too_large`).

## Invariants — keep them true

- **The two guard files must contain identical directives** (comments
  aside). `run-tests.sh` diffs them and aborts if they differ.
- **Distributed guard files contain no active allowed URL** (examples are
  commented). The test script injects the test URLs before the first line
  containing `ENGINE`. Keep a line with the word `ENGINE` before the engine
  in both files, and do not use that word earlier.
- **No trailing comments on directive lines** (Apache reads them as
  arguments). Comments go on their own line.
- The OBSERVE toggle line must stay exactly `#SetEnvIf Request_URI ^ MPG_OBSERVE=1`
  (the test script uncomments it with sed).
- Size limit default `8323072` = 8M − 64 KB, same number on both lines
  (`MPG_MAX_BYTES` and `LimitRequestBody`).

## How the engine works (and why)

- `SetEnvIfExpr` lines (mod_setenvif) classify the request. In `.htaccess`
  / `<Location>` they run at the **header_parser** phase: after URL
  decoding/normalisation, before authorization and before the handler.
  First match wins via the `%{ENV:MPG} == 'seen'` guard on each rule.
- **`<If>` is evaluated BEFORE the per-dir SetEnvIf lines** (if_walk runs
  before header_parser). So `<If>` cannot read `MPG`; it only selects
  candidate requests (multipart, POST, internal redirect of a refused one).
  The decision is a **`Require expr`** inside it, evaluated at authz time,
  when `MPG` is known. `AuthMerging And` keeps the site's own access rules.
- Only the original request is classified (`-z %{ENV:REDIRECT_STATUS}`);
  an internal redirect of a refused request (`REDIRECT_MPG` = `deny*`) is
  refused too (blocks an `ErrorDocument` pointing to PHP).
- `LimitRequestBody` inside `<If POST>` handles chunked bodies; the
  Content-Length rule handles declared sizes.

## Findings (measured on the test bench — do not re-discover)

- PHP truncates the MIME type at `;`, `,` or space, lowercases it: it parses
  `multipart/form-data,x` and `multipart/form-data x`. A regex like
  `^multipart/form-data([[:space:]]*;|$)` misses both → detection is the
  substring `multipart`, case-insensitive. Tab, `Content_Type`, folded
  `multipart/form-\r\n data` are NOT parsed by PHP.
- PHP finds `boundary=` by substring: `xboundary=AAA; boundary=XyZ` → `AAA`.
- **mod_rewrite edition bypass**: a sub-folder `.htaccess` with
  `RewriteEngine Off` disables inherited rules (test M19).
  `RewriteOptions InheritDownBefore` only fixes `RewriteEngine On`.
  → reason the guard uses mod_setenvif + `<If>`/`Require`.
- **`ProxyPassMatch` (PHP-FPM) never reads `.htaccess`**; the multipart
  reached PHP's parser even for a non-existent script. `<Location>` sections
  ARE evaluated → install in the VirtualHost `<Location "/">` (same file).
- `LimitRequestBody` alone does not prevent the post_max_size warning when
  Content-Length is declared (PHP reads the header first) → the
  Content-Length rule is required.
- Chunked bodies: mod_fcgid buffers and overshoots `LimitRequestBody` by up
  to 8 KB (HUGE_STRING_LEN) → limit = post_max_size − 64 KB.
  mod_php: 413, PHP got exactly the limit. mod_fcgid/proxy_fcgi: PHP gets a
  truncated body and answers 200. proxy_fcgi + php-cgi received 0 bytes of a
  chunked body (real PHP-FPM untested).
- Refused requests with an oversize body may answer **413 instead of 403**
  (Apache hits LimitRequestBody while discarding the body). Both count as
  "refused" in the tests.
- **PHP warning wording differs**: PHP 8 `PHP Request Startup: POST
  Content-Length ... exceeds the limit`; PHP 7.4 `Unknown: POST
  Content-Length ... exceeds the limit`. The test counter matches
  `allowable file uploads|exceeds the limit|Actual POST length`.
- An `ErrorDocument` internal redirect turns POST into GET → the log uses
  `%<m` and `%<{MPG}e` (original request).
- A typo in `MPG_MAX_BYTES` (e.g. `10M`) blocks all uploads (fail closed)
  but not plain forms (the generic POST rule checks the value is numeric).
- WordPress upload URLs were checked in WordPress 7.1.3 source:
  `/wp-admin/async-upload.php`, `/wp-json/wp/v2/media`,
  `/wp-json/wp/v2/media/<id>/sideload`, `/wp-admin/nav-menus.php` (menu
  forms are multipart!), plus occasional ones (update.php, media-new.php,
  media-upload.php, themes.php, admin.php, network/site-new.php). Plain
  permalinks: `/index.php?rest_route=/wp/v2/media`.

## Proof that PHP received nothing

`tests/canary.bin` has 21 files while `max_file_uploads = 20`: if PHP's
multipart parser runs, it logs "Maximum number of allowable file uploads"
to `c:/wamp64/logs/php_error.log` **before any script**. A refusal passes
only if: status 403/413, no `PHP_REACHED` marker, no new warning. Test A2
(allowed URL) is the positive control. Size tests use the post_max_size
warning the same way.
